01The 1-minute pitch

Memorise this. It is your opening answer to "Tell us about your project".

Say this

SchedFS is a responsiveness-focused file system with deadline-aware request scheduling. Our aim was to build a mountable Linux file system that keeps everyday file operations responsive during competing bulk transfers by scheduling storage requests with deadlines, while keeping useful throughput for background work. It is written in C on FUSE: you mount it and use mkdir, cp and cat as usual. Every block it reads or writes waits in one queue, and one dispatcher thread serves the queue in the order a policy chooses. Our deadline policy serves reads at once, oldest first, and lets writes be ordered by locality for at most 2 ms. On one Windows + WSL 2 machine, small reads during background writes had a 22 to 56% lower 99th-percentile latency than under our own FCFS policy, with background throughput within −13% to +8% of FCFS. The cost: SSTF keeps more throughput when seek time is modeled, and small foreground updates with real I/O got 24% slower.

Key ideaIf you remember one sentence: every block waits in one queue; reads become urgent at once, writes after 2 ms, and urgent requests go first. And: we compare policies inside SchedFS on identical workloads, not SchedFS against the kernel.

02The problem and our idea

The problem

  • Bulk transfers and small operations share one disk: while a backup, an import or a large copy runs, you still want to open a config file or save your notes without a long pause.
  • Arrival order makes small reads wait: under FCFS a small read queues behind every background write that arrived first.
  • Locality alone can starve: SSTF always serves the nearest block, so a distant small read can be overtaken again and again by nearby background writes.
  • A small operation is a chain: one open + 4 KB read + close needed about 11 block requests in our experiments (path lookup, inode, data), so every wait is paid many times.

Our solution in three parts

  • A real file system in user space using FUSE: folders, files, reading, writing, renaming and deleting all work with ordinary Linux commands.
  • Deadline-aware scheduling in the request path: every block request goes through a bounded queue, and a policy chosen at mount time orders it. The deadline policy gives each request a service-start deadline and serves overdue requests first, otherwise the nearest block.
  • Honest measurement: a per-request trace, a workload generator and repeated mounted experiments (3 runs × 10 s per cell), kept separate from a deterministic simulation. Modeled movement is never presented as a speed-up.
Be preciseDeadline scheduling is an established idea (the Linux deadline I/O scheduler also gives reads and writes separate expiry times). Our contribution is implementing it, with the textbook policies, in a working file system's request path, and evaluating it on mounted workloads.

04The full flow, step by step

Follow one small read while two background writers are copying large files: cat mnt/notes/today.txt.

  1. Your program calls read()Program

    cat opens the file inside the mounted folder and calls the read() system call.

  2. The kernel hands it to FUSEKernel

    Linux's virtual file system sees a FUSE mount and passes the call through /dev/fuse to our running schedfs program.

  3. The FUSE adapter receives itM2

    op_read in fuse_main.c records the calling process (for the trace only) and calls sfs_read. Several FUSE threads do this for many programs at once.

  4. The file system finds the blockM3 · M4

    lookup_locked holds the namespace lock while it resolves the path, takes the file's reader lock, and only then lets go of the namespace lock. bmap says which disk block holds the bytes.

  5. A request joins the queueM5

    The work becomes a request: read or write, block number, buffer, arrival time. It goes into the bounded queue (at most 128) next to the background writers' requests. The thread then sleeps on its own "done" condition variable.

  6. The scheduler applies the deadline ruleM6

    The dispatcher asks scheduler_pick. A read's deadline is arrival + 0 ms, so it is overdue at once; if it has the earliest deadline among overdue requests, it is served next. If nothing is overdue, the nearest block is served.

  7. The dispatcher does the real I/OM7

    The one dispatcher thread moves the head with scheduler_advance, calls pread on disk.img (with O_DIRECT in the experiments), waits out the modeled service time if one is set, and records wait, movement and queue depth.

  8. The caller wakes and the answer goes backM7 → Program

    The dispatcher sets completed and signals. The thread wakes, unlocks the file, and the data travels back through FUSE. The other block requests of the same cat make the same trip.

While the thread sleeps it still holds the file's lock (and, for create, rename or unlink, the namespace lock). That is safe because the dispatcher never needs those locks: it takes only the queue mutex and the request's own mutex.

Mounting SchedFS

Serving one block request

The states, in one line each

  • A request: Created → Queued → becomes overdue at its deadline (deadline policy) → Picked → In service (pread/pwrite) → Completed, and the caller is woken. It lives on the caller's stack, so nothing is allocated per I/O.
  • A block: Free (bitmap bit 0) → Allocated (bit 1, zero-filled) → Free again when its file is deleted or truncated.
  • An inode: Allocated → in use (operations hold its lock) → name removed under the namespace lock → freed only under its write lock, so nobody still using it sees it reused.
  • The mount: Formatted by mkfs.schedfs → Mounted (validated, then the daemon starts the dispatcher) → Unmounted, with requests, movement, mean and maximum wait and maximum queue depth written to filesystem.log.

05The tech stack, explained simply

For each tool: what it is and why we picked it. Examiners like the "why".

Language
C (gnu11)

The language of operating systems. It gives direct control over bytes, structs and threads, so the on-disk format is exact: a 128-byte inode is checked at compile time.

File-system interface
libfuse 3

Lets an ordinary program act as a file system. The kernel forwards each system call on the mount to our callbacks, so a bug cannot crash the computer.

Concurrency
POSIX threads

Mutexes, condition variables and reader-writer locks for the namespace, each file, the queue, the bitmap and the inode table. FUSE runs requests on several threads.

Disk I/O
pread, pwrite, O_DIRECT

Read or write exactly one 4 KB block at an offset. With --direct-io the host page cache is bypassed, so requests really reach the (virtual) disk and overlap in the queue.

Build
GCC and Make

make builds four programs: schedfs, mkfs.schedfs, schedfs-bench (simulation) and schedfs-workload. make unit, make test and make tsan run the tests.

Checking
ThreadSanitizer

A compiler tool that reports two threads touching the same data without a lock. make tsan runs the core and regression tests under it; clean in repeated runs.

Experiments
Python, matplotlib

experiments.py runs the tuning and evaluation matrices, analyze_run.py computes percentiles, report_results.py writes summary.md and the charts.

Tools
Docker on WSL 2, Git

docker/Dockerfile gives Ubuntu 24.04 with /dev/fuse on a Windows laptop; every test and measurement ran there as a normal user.

How a request travels (the restaurant picture)

Think of a restaurant with one chef and many waiters:

  • The kernel and FUSE = the front door: every customer (system call) comes in here and is sent to our restaurant.
  • FUSE threads = the waiters: several take orders at the same time and pin each order (a request) on the rail.
  • The bounded queue = the order rail: it holds at most 128 tickets. When it is full, waiters wait.
  • The deadline policy = the chef's rule: a ticket for a quick order (a read) is urgent at once; a big order (a write) becomes urgent after 2 minutes. Urgent tickets first, oldest urgent first; otherwise cook whatever is closest at hand.
  • The dispatcher = the one chef who cooks (does the disk I/O), then rings the bell for that ticket's waiter.

07The disk layout

The "disk" is one file. mkfs.schedfs disk.img 16M splits it into 4,096 blocks of 4 KB, in four regions (the experiments use 64 MiB images, 16,384 blocks).

RegionBlocksWhat it stores
Superblock0The disk's ID card: magic number 0x53465331, version, block size, total and free blocks and inodes, and where each region starts.
Free-space bitmap1One bit per block: 1 = used, 0 = free. 4,096 bits fit in one block.
Inode table2 – 9256 inodes of 128 bytes, 32 per block. Inode 1 is the root folder.
Data blocks10 – 4,095File contents, folder entries and indirect pointer blocks. Block 10 is the root folder's first block.
StructureSizeWhat is inside
Inode128 bytesType and permission bits, link count, owner, size, three timestamps, 12 direct block pointers and 1 single-indirect pointer.
Indirect block4 KB1,024 more block numbers (4 bytes each) for files bigger than 12 blocks.
Directory entry64 bytesAn inode number and a name of up to 59 characters. A folder is a file full of these.
  • Biggest file: 12 + 1,024 = 1,036 blocks, about 4.05 MiB. One block more returns "File too large" (EFBIG).
  • Holes: a block pointer of 0 means "not written yet". Reading it gives zeros, so truncate -s 8192 grows a file without using any blocks.
  • The tail rule: bytes of the last block beyond the file size are always zero. Shrinking inside a block zeroes the cut-off part, so growing the file again shows zeros, not old bytes (finding B).
  • Keeping files together: a new block is searched for right after the file's previous block first, so a file's blocks sit side by side.
Good to mentionThe sizes are guaranteed by the compiler: _Static_assert checks that the superblock header and an inode are exactly 128 bytes and a directory entry 64 bytes. On mount, a wrong magic number, version, block size or root inode is refused.

08Disk scheduling, the heart of the project

Expect most questions here. Learn the six policies, the deadline rule and its limits, why Adaptive can starve, and the measured results with their cost.

Six policies, one question

Every policy answers: which waiting request should the disk serve next? All of them break ties by arrival time, then by request ID, so the same input always gives the same order.

PolicyRuleGood atWeak at
FCFSOldest request first, like a ticket queue.Fair; nobody waits forever.A small read waits behind every queued write.
SSTFNearest block to the head first.Least movement, most throughput.A distant request can starve.
SCANMove one way serving requests, go to the disk edge, turn (the lift).Even sweep.The edge trips cost time on the modeled disk.
LOOKLike SCAN, but turn at the last request.SCAN without the edge trip.A request just behind the head waits a full sweep.
AdaptiveLowest α·distance/N − β·wait/longest wait.A heuristic blend of distance and age.No starvation guarantee (see below).
DeadlineOverdue requests first, earliest deadline first; otherwise the nearest block.Reads served promptly; writes keep some locality.Gives up part of SSTF's throughput; not real-time.

The deadline rule

deadline = arrival + 0 ms   (reads,  --read-deadline-ms)
deadline = arrival + 2 ms   (writes, --write-deadline-ms)
if any request is overdue (deadline <= now): serve the earliest deadline (ties: arrival, id)
else:                                         serve the nearest block (SSTF)
  • In practice: every read is overdue at once, so reads are served oldest first. A write younger than 2 ms can be passed by reads and by nearer writes; after 2 ms it is served in deadline order.
  • Limits: both deadlines 0 gives FCFS; very long deadlines give SSTF. Both are checked in the unit test (640 and 236 on the textbook trace).
  • Within one type a later request can never overtake an overdue one, because every deadline is arrival + the same constant. Across types a read can pass an overdue write only if the read arrived before the write's deadline, so a stream of reads cannot starve a write.
  • Bound: an overdue request R starts no later than deadline(R) + (Q − 1 + P) · Smax + Scurrent (Q = queue capacity, P = producers blocked at admission, S = service times). The dispatcher is non-preemptive, so this is not a real-time guarantee.
  • How the values were chosen: on separate tuning runs (seed 101, never used in the evaluation). Read deadline 0 ms gave the lowest tail (mean p99/FCFS 0.69). A 50 ms write deadline made foreground updates worse, so writes were re-tuned: 2 ms (1 ms cost 22% throughput in one cell).

Why Adaptive can starve (finding C)

score = α · (distance ÷ N) − β · (wait ÷ longest wait)      α = 0.7, β = 0.3, lowest wins
  • The age part is divided by the longest wait in the queue, so it is never worth more than β, however long a request has waited.
  • So a request more than (β/α) · N ≈ 0.43 · N blocks farther than nearby work never wins while nearby work keeps arriving. Test: 0 picks in 10,000 decisions for a request 3,000 blocks away (N = 4,096); a request 1,200 blocks away is chosen at once.
  • Our first report called this "ageing that prevents starvation". That was wrong, and we corrected it. Adaptive is now a documented heuristic baseline.

09Synchronization and the dispatcher

Our central rule: many producers, one consumer. Many FUSE threads create requests; exactly one dispatcher thread serves them.

  • Bounded buffer: one mutex guards an array of up to 128 requests. A producer that finds it full sleeps on not_full; the dispatcher that finds it empty sleeps on not_empty. No busy waiting.
  • Always re-check: every pthread_cond_wait sits inside a while loop, so a spurious wake-up is harmless.
  • Per-request "done" signal: each request has its own mutex, condition variable and completed flag. The flag is set under that mutex before signalling, so a wake-up can never be lost.
  • Namespace lock (ns_lock): a reader-writer lock on the directory tree. Create, mkdir, unlink, rmdir and rename take it for writing; lookups take it for reading only until they hold the file's lock.
  • Readers-writers on files: each inode has a reader-writer lock. Many threads can read a file together; a write, truncate or free gets it alone.
  • Metadata order: bitmap_io_lock and super_io_lock keep each snapshot together with its write, so an older bitmap can never overwrite a newer one on disk.

How deadlock is prevented

Locks are always taken in one global order, so a circular wait cannot form:

ns_lock → inode lock → directory lock → inode-alloc → inode-table
  → bitmap I/O → bitmap → superblock I/O → superblock → queue mutex → request mutex
SafeguardWhy
Dispatcher uses only two locksThe queue mutex and the request's own mutex, one at a time. A thread that holds file locks while it waits for its I/O can never block the thread that will wake it.
Queue mutex never held during I/OThe dispatcher takes the request out and releases the mutex before pread/pwrite.
Inode freed under its write lockunlink removes the name under ns_lock, then waits for the inode's write lock before freeing blocks, so readers and writers still using it finish first.
Dispatcher started in op_initFUSE calls fork() to go into the background, and only the calling thread survives a fork.

11Bugs we found and fixed

Showing that you found and fixed your own bugs, and corrected your own claims, impresses examiners.

From the first version

  1. Lost inode updates. 32 inodes share one 4 KB block, so two threads changing different inodes could each write back their own copy. An inode-table mutex fixed it.
  2. Hang when mounted in the background. Threads do not survive fork(), so the dispatcher vanished. It now starts in FUSE's init callback.
  3. Image not found after going to the background. The daemon changes its folder to /; paths are now made absolute with realpath.

13Limitations and future scope

Be honest here. Admitting limits clearly is a strength in a viva.

Limitations

  • One machine, no real hard disk: all measurements are from one Windows 11 + WSL 2 machine. The "model" configuration's seek time is a model.
  • Reads only: the policy helps foreground reads during background writes. Foreground updates with real I/O got 24% slower than FCFS, and with 4 writers on the modeled disk LOOK was slightly better.
  • Not real-time: the dispatcher is non-preemptive and an operation is a chain of requests, so no completion time is promised.
  • Read or write only: requests are classified by operation type; there is no per-process or per-file priority.
  • FUSE is slow: about two orders of magnitude slower per operation than the host file system with its page cache.
  • No journal: a clean unmount is needed. Files up to 1,036 blocks (about 4.05 MiB), 256 inodes, no links, no permission enforcement.

Future scope

  • Give a foreground write its own, shorter deadline (for example by caller), to fix the update regression.
  • Measure on a physical hard disk and on other machines.
  • A journal and an fsck tool for crash safety; double-indirect blocks for bigger files.
  • A block cache, and C-SCAN as another baseline.

16Likely viva questions

Basics

What does SchedFS do?
It is a mountable Linux file system in user space whose every block read and write waits in one queue, served in the order a policy chooses. Its deadline policy keeps small file operations responsive while bulk transfers run, at a measured cost in throughput.
Why FUSE?
The whole file system runs as an ordinary process: we can trace every request, change the scheduler with a flag, and a bug cannot crash the kernel. The kernel still delivers real system calls from real programs. The cost is extra context switches per operation, which is why we compare policies inside SchedFS rather than claiming SchedFS is faster than a kernel file system.
Where is the disk?
One ordinary file, disk.img, treated as numbered 4 KB blocks. Only the dispatcher thread reads or writes it; in the experiments it is opened with O_DIRECT so requests reach the WSL 2 virtual disk instead of the host page cache.

The deadline policy

Explain the deadline policy.
Each request gets a deadline: arrival + 0 ms for reads, arrival + 2 ms for writes. If any request is overdue, the one with the earliest deadline is served; otherwise the nearest block. So reads go first, oldest first, and writes are ordered by locality for at most about 2 ms.
Is this your invention?
No. Deadline scheduling is established; the Linux deadline I/O scheduler also gives reads and writes separate expiry times. Our contribution is implementing it, with five other policies, in a working file system's request path, and evaluating it on mounted workloads with the same instrumentation.
Why might the policy help?
A small file operation is a chain of about 11 dependent block requests, and each waits behind whatever is queued. Under FCFS each read waits for the writes ahead of it; under SSTF a distant read can wait for many nearby writes. Deadline serves reads first and keeps the writes ordered by locality, so reads stop queueing behind writes while writes keep much of SSTF's short movement.
Can a request still wait a long time?
Yes, within limits. The dispatcher is non-preemptive, so an overdue request still waits for the one in service and for requests with earlier deadlines: at most queue capacity − 1 plus producers blocked at admission. A write waits up to its 2 ms deadline plus that. A file operation can take longer than any one deadline because it is a chain. Deadlines are not real-time guarantees.
What happens under overload?
Every request becomes overdue, so the policy becomes earliest-deadline-first: FCFS within each type, reads before writes of the same age. Queues and waits grow as under FCFS; the bounded queue (128) blocks producers instead of using unbounded memory. Nothing is dropped.
How were 0 ms and 2 ms chosen?
On separate tuning runs with seed 101, never used in the evaluation. 0 ms for reads gave the lowest tail (mean p99/FCFS 0.69). A 50 ms write deadline made foreground updates worse, so writes were re-tuned; 2 ms was chosen because 1 ms cost 22% of throughput in one cell.

Results and honesty

What is modeled and what is measured?
Measured: the end-to-end latency of every foreground operation (the workload's own clock), background bytes per second, and per block request its arrival, start and end, queue depth and caller (the trace). Modeled: "movement" (block distance) and, in the model configuration, the service time (100 µs + 0.25 µs per block moved), standing in for a disk where position matters. The direct configuration has no modeled delay. The simulator (schedfs-bench) is a model end to end.
What is the throughput trade-off?
Against FCFS it is small: −13% to +6% (direct, mostly within run-to-run ranges) and −9% to +15% (model). Against SSTF, Deadline gives up 20 to 60% of background throughput on the modeled disk, because it uses locality only within the 2 ms window; in return its foreground p99 was 30 to 79% lower than SSTF's.
What does this improve over, exactly?
Over SchedFS's own FCFS, SSTF, SCAN, LOOK and Adaptive policies, on the same mounted file system and identical workloads, for small foreground reads while background processes write or copy: p99 22 to 56% lower than FCFS. It does not improve foreground updates with real I/O (+24% vs FCFS), and LOOK was slightly better with 4 writers on the modeled disk. It makes no claim about kernel file systems or kernel I/O schedulers; the host-file-system numbers are a reference only.
Why did updates get worse?
The foreground's own block writes are treated like background writes: they get the 2 ms write deadline and can wait behind other overdue writes. Classification is by operation type only.
Is the difference real or noise?
For the six read cells, the three-run ranges of Deadline and FCFS do not overlap. For direct updates the ranges also do not overlap, so the regression is real too. With no background load all policies are within each other's ranges.
Which claims are supported by which tests?
Exact orders and limits: test_scheduler. SCAN 236 / LOOK 208 everywhere: test_scheduler and test_regress (real dispatcher). Overdue requests not bypassed: test_starvation, test_deadline_order. Adaptive can starve: test_adaptive_bound. Truncate, create, unlink, rename fixed: test_regress, and check_old_defects.sh shows them failing on the old code. No races seen: make tsan (supporting evidence only). Works mounted under every policy and persists: system.sh. Lower tail latency at a throughput cost: experiments.py matrix and results/mounted/summary.md.

Scheduling basics

Explain FCFS, SSTF, SCAN and LOOK.
FCFS serves in arrival order. SSTF serves the request nearest the head. SCAN moves one way serving requests, goes to the disk edge, then reverses, like a lift. LOOK reverses at the last request instead of the edge.
Does Adaptive prevent starvation?
No. Its age term is divided by the longest wait, so it is never worth more than β = 0.3. A request more than about 0.43 × N blocks farther than nearby work never wins while nearby work keeps arriving: 0 picks in 10,000 decisions. Our first report said otherwise; we corrected it.
Why is SCAN so slow on the modeled disk?
Every reversal pays the trip to the disk edge (16,384 blocks), and on the modeled disk that costs time: p99 82 to 119 ms with background load and 36.7 ms even with none. LOOK is the practical variant.
Why are the results deterministic?
Ties are broken by arrival time and then request ID, and the scheduler takes the current time as an argument. The tests and the simulator use a simulated clock, so every policy, even Deadline and Adaptive, gives exactly the same result every run. Mounted runs are measurements and vary, which is why we repeat them.

Synchronization

Which classic problem is the queue?
The bounded-buffer (producer-consumer) problem: FUSE threads produce requests, the dispatcher consumes them, and a mutex with not_full and not_empty condition variables coordinates them.
How do you prevent deadlock?
One global lock order, from ns_lock down to the per-request mutex; a lock later in the order is never held while an earlier one is requested. The dispatcher takes only the queue mutex and a request's own mutex, so a thread waiting for its I/O while holding file locks cannot block it.
What was the unlink bug?
unlink freed a file's blocks and inode without the inode lock that readers and writers hold. A reader that had already looked up the name could then read blocks of a different file that reused them. Now lookups hold the namespace lock until they hold the inode lock, and unlink frees only under the inode's write lock.
Does a clean ThreadSanitizer run prove there are no races?
No. It only sees the interleavings that happened. That is why we also have targeted regression tests that fail on the old code. TSan was clean in repeated runs; one early run failed once with a message we did not capture.

17Glossary

TermMeaning in one line
File systemThe rules for where each file's bytes live on a disk and how names map to them.
FUSEFilesystem in Userspace: a normal program acting as a file system.
BlockA fixed 4 KB piece of the disk; the unit of every read and write.
SuperblockBlock 0: the disk's size, layout and free counts.
BitmapOne bit per block: used or free.
InodeA 128-byte record describing one file or folder and where its blocks are.
Indexed allocationKeeping a list of a file's block numbers in its inode (direct and indirect).
MovementHow many blocks the modeled head moves between two requests; a model, not a measurement.
LOOKLike SCAN, but the head turns at the last request instead of the disk edge.
DeadlineThe time by which a request should start: arrival + 0 ms (read) or + 2 ms (write). After it, the request is overdue.
StarvationA request that keeps getting skipped and waits indefinitely.
p99The 99th percentile: 99% of operations were faster than this; it describes the slow tail.
O_DIRECTAn open flag that bypasses the host page cache, so each read or write reaches the device.
Modeled service timeAn added hold of 100 µs + 0.25 µs per block moved, standing in for a disk where position matters.
SimulationRunning the real scheduler on given arrivals with a simulated clock; repeatable, but not a measurement.
MutexA lock only one thread can hold at a time.
Condition variableA way for a thread to sleep until another signals that something changed.
Reader-writer lockA lock many readers can share but a writer must hold alone.
Bounded bufferA fixed-size queue shared by producers and consumers.
DeadlockThreads each waiting for a lock another holds, so none can move.
Data raceTwo threads touching the same memory without a lock, at least one writing.
Regression testA test that stops a fixed bug from coming back.
