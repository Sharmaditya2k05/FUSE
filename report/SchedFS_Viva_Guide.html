01The 1-minute pitch

Memorise this. It is your opening answer to "Tell us about your project".

Say this

SchedFS is a real file system for Linux that we wrote in C. You mount it like a pen drive and use normal commands such as mkdir, cp and cat inside it. The "disk" is one 16 MiB file, split into 4,096 blocks of 4 KB. What makes it special is that every block it reads or writes first goes into a waiting queue, and a scheduler decides which request the disk serves next, using FCFS, SSTF, SCAN or our own Adaptive policy that balances distance and waiting time. One dispatcher thread does all the disk I/O, like a single disk arm. So three textbook topics, file systems, disk scheduling and thread synchronization, run together on real traffic. On a real mounted workload of 4,927 requests, SSTF cut head movement by 40% compared with FCFS. It is built with libfuse 3 and POSIX threads, and is checked by 25 test cases and ThreadSanitizer.

Key ideaIf you remember one sentence: every block waits its turn in one queue, and the scheduler decides the turn. And: same requests, different order, different head movement.

02The problem and our idea

What is wrong today

  • Taught in separate boxes: textbooks teach file systems, disk scheduling and synchronization as three separate chapters, so students never see them working together.
  • Scheduling stays on paper: disk-scheduling problems are solved by hand on a list of numbers like 98, 183, 37. Nobody sees the policy run on real file traffic.
  • The kernel hides it: a real Linux file system lives inside the kernel, where its queue and scheduler are hard to see, change or measure.
  • Kernel code is risky: a bug in a kernel module can crash the whole computer, which makes it a poor place to experiment.

Our solution in three parts

  • A real file system in user space using FUSE: folders, files, reading, writing, renaming and deleting all work with ordinary Linux commands.
  • A visible scheduling layer: every block request goes through a bounded queue, and a pluggable scheduler (FCFS, SSTF, SCAN or Adaptive) chooses the order. You pick the policy when you mount.
  • Measurement built in: the dispatcher counts requests, head movement and waiting time, and a benchmark replays fixed traces under every policy so they can be compared fairly.

04The full flow, step by step

Follow one real example from our demo: you type echo 'Operating Systems' > mnt/project/demo.txt.

  1. Your program calls write()Program

    The shell opens demo.txt inside the mounted folder and calls the write() system call with 18 bytes.

  2. The kernel hands it to FUSEKernel

    Linux's virtual file system sees that the folder is a FUSE mount, so it passes the request through /dev/fuse to our running schedfs program.

  3. The FUSE adapter receives itM2

    op_write in fuse_main.c calls the file-system function sfs_write. A pool of FUSE threads can do this for many programs at once.

  4. The file system finds the blockM3 · M4

    It looks up the path, takes the file's writer lock, and asks bmap which disk block holds byte 0. The file is new, so it takes a free block from the bitmap, preferring the block right after the file's previous one.

  5. A request joins the queueM5

    The work becomes a request: read or write, block number, buffer, arrival time. It goes into the bounded queue (at most 128). The calling thread then sleeps on its own "done" condition variable.

  6. The scheduler picks the next requestM6

    The dispatcher wakes up and asks scheduler_pick which waiting request to serve. FCFS takes the oldest, SSTF the nearest, SCAN the nearest in the current direction, Adaptive the lowest score.

  7. The dispatcher does the real I/OM7

    The single dispatcher thread calls pwrite on disk.img at block × 4096, records the seek distance and waiting time, and moves the head to the new block.

  8. The caller wakes and the answer goes backM7 → Program

    The dispatcher sets completed and signals the request's condition variable. The sleeping thread wakes, the reply travels back through FUSE and the kernel, and write() returns 18.

One file operation can make several block requests (inode, bitmap, superblock, data block), and each one takes this same trip through the queue.

Mounting SchedFS

Serving one block request

The states, in one line each

  • A request: Created → Queued → Picked by the scheduler → In service (pread/pwrite) → Completed, and the caller is woken. It lives on the caller's stack, so nothing is allocated per I/O.
  • A block: Free (bitmap bit 0) → Allocated (bit 1, zero-filled) → Free again when its file is deleted or truncated.
  • The mount: Formatted by mkfs.schedfs → Mounted (validated, then the daemon starts the dispatcher) → Unmounted, with "requests served and total seek" written to filesystem.log.

05The tech stack, explained simply

For each tool: what it is and why we picked it. Examiners like the "why".

Language
C (gnu11)

The language of operating systems. It gives direct control over bytes, structs and threads, so the on-disk format is exact: a 128-byte inode is checked at compile time.

File-system interface
libfuse 3

Lets an ordinary program act as a file system. The kernel forwards each system call on the mount to our callbacks, so a bug cannot crash the computer.

Concurrency
POSIX threads

Mutexes, condition variables and reader-writer locks for the queue, the bitmap, the inode table and each file. FUSE runs requests on several threads.

Disk I/O
pread, pwrite, fsync

Read or write exactly one 4 KB block at an offset, without moving a shared file position, so only the dispatcher touches the image.

Build
GCC and Make

One make builds three programs: schedfs, mkfs.schedfs and schedfs-bench. Strict warnings are on (-Wall -Wextra -Wpedantic -Wconversion).

Checking
ThreadSanitizer

A compiler tool that watches every memory access at run time and reports two threads touching the same data without a lock. It found one race, which we fixed.

Graphs
Python, pandas, matplotlib

generate_workload.py makes traces and plot_results.py turns benchmark.csv into comparison charts.

Tools
Docker, Git, GitHub Pages

Docker runs Ubuntu 24.04 with /dev/fuse on a Windows laptop. GitHub hosts the code and an interactive scheduler demo page.

How a request travels (the restaurant picture)

Think of a restaurant with one chef and many waiters:

  • The kernel and FUSE = the front door: every customer (system call) comes in here and is sent to our restaurant.
  • FUSE threads = the waiters: several take orders at the same time and pin each order (a request) on the rail.
  • The bounded queue = the order rail: it holds at most 128 tickets. When it is full, waiters wait.
  • The scheduler = the head chef's rule for which ticket to cook next: oldest first, nearest first, or sweep along the rail.
  • The dispatcher = the one chef who cooks (does the disk I/O), then rings the bell for that ticket's waiter.

The rules live in clear places: scheduler.c chooses, virtual_disk.c serves, and request_queue.c holds the waiting line.

07The disk layout

The "disk" is one file. mkfs.schedfs disk.img 16M splits it into 4,096 blocks of 4 KB, in four regions.

RegionBlocksWhat it stores
Superblock0The disk's ID card: magic number 0x53465331, version, block size, total and free blocks and inodes, and where each region starts.
Free-space bitmap1One bit per block: 1 = used, 0 = free. 4,096 bits fit in one block.
Inode table2 – 9256 inodes of 128 bytes, 32 per block. Inode 1 is the root folder.
Data blocks10 – 4,095File contents, folder entries and indirect pointer blocks. Block 10 is the root folder's first block.
StructureSizeWhat is inside
Inode128 bytesType and permission bits, link count, owner, size, three timestamps, 12 direct block pointers and 1 single-indirect pointer.
Indirect block4 KB1,024 more block numbers (4 bytes each) for files bigger than 12 blocks.
Directory entry64 bytesAn inode number and a name of up to 59 characters. A folder is a file full of these.
  • Biggest file: 12 + 1,024 = 1,036 blocks, about 4.05 MiB. One block more returns "File too large" (EFBIG).
  • Holes: a block pointer of 0 means "not written yet". Reading it gives zeros, so truncate -s 8192 grows a file without using any blocks.
  • Keeping files together: a new block is searched for right after the file's previous block first, so a file's blocks sit side by side and reading it needs short seeks.
  • Opening a path: /project/demo.txt = read the root folder (inode 1), find project, read that folder, find demo.txt.
Good to mentionThe sizes are guaranteed by the compiler: _Static_assert checks that the superblock header and an inode are exactly 128 bytes and a directory entry 64 bytes. On mount, a wrong magic number, version, block size or root inode is refused, so a random file is never treated as a SchedFS disk.

08Disk scheduling, the heart of the project

Expect most questions here. Learn the four policies, the Adaptive formula, the worked example and the real results.

Four policies, one question

Every policy answers: which waiting request should the disk serve next? All of them break ties by arrival time, then by request ID, so the same input always gives the same order.

PolicyRuleGood atWeak at
FCFSOldest request first, like a ticket queue.Fair; nobody waits forever.The head zig-zags; long seeks.
SSTFNearest block to the head first.Shortest seeks on scattered traffic.A far request can starve.
SCANKeep moving one way, serve requests on the way, then turn around (the lift).Short seeks and fair to both ends.Requests just behind the head wait a full sweep.
AdaptiveLowest score wins; the score mixes distance and waiting time.Tunable between speed and fairness.Needs tuning for each workload.

The Adaptive score in plain words

score = α · (distance ÷ total blocks) − β · (wait ÷ longest wait)      α = 0.7, β = 0.3
  • A near request makes the first part small; an old request makes the second part large. Both lower the score, and the lowest score is served.
  • The longer a request waits, the better its score gets, until it wins. This is ageing, the classic cure for starvation.
  • With β = 0 Adaptive is exactly SSTF. A larger β moves it toward FCFS. Both weights are set at mount time with --alpha and --beta.
  • Adaptive reads the real clock to measure waiting time, so its totals can shift slightly between runs. FCFS, SSTF and SCAN are exactly repeatable.

09Synchronization and the dispatcher

Our central rule: many producers, one consumer. Many FUSE threads create requests; exactly one dispatcher thread serves them.

  • Bounded buffer: one mutex guards an array of up to 128 requests. A producer that finds it full sleeps on not_full; the dispatcher that finds it empty sleeps on not_empty. No busy waiting.
  • Always re-check: every pthread_cond_wait sits inside a while loop, so a spurious wake-up is harmless.
  • Per-request "done" signal: each request has its own mutex, condition variable and completed flag. The dispatcher sets the flag under that mutex before signalling, so a wake-up can never be lost.
  • Readers-writers on files: each inode has a reader-writer lock. Many threads can read a file together; a write gets it alone.
  • Shared metadata: separate mutexes for each directory, inode allocation, the inode table, the bitmap and the superblock.
  • Why one dispatcher? "Head position" only means something if one place serves requests in order, like a real disk arm. It also lets the scheduler see every waiting request when it chooses.

How deadlock is prevented

Locks are always taken in one global order, so a circular wait cannot form:

directory → inode rwlock → inode-alloc → inode-table → bitmap → superblock → queue
SafeguardWhy
Queue mutex taken lastAnd never held during pread/pwrite, so slow I/O never blocks other threads from queueing.
Request mutex never nestedThe per-request completion lock is never held together with any other lock.
Dispatcher uses only two locksThe queue mutex and the request's own mutex, so a thread holding file locks while it waits for I/O cannot block it.
Bitmap snapshotThe bitmap is copied under bitmap_lock before it is written to disk, so the copy cannot change halfway.
Dispatcher started in op_initFUSE calls fork() to go into the background, and only the calling thread survives a fork. Starting the dispatcher after the fork keeps it alive.

11Bugs we found and fixed

Showing that you found and fixed your own bugs impresses examiners.

  1. Lost inode updates. 32 inodes share one 4 KB block, so changing one is read, change, write back. Two threads changing different inodes in the same block could each write back their own copy, and one update was lost. test_core failed about 30% of runs. A new inode-table mutex fixed it: 0 failures in 100 runs.
  2. Bitmap race found by ThreadSanitizer. The bitmap was handed to the dispatcher while another thread could still change it. It is now copied under bitmap_lock first.
  3. Hang when mounted in the background. Without -f, FUSE forks into the background, and threads do not survive fork(). The dispatcher vanished, so the first mkdir waited forever. The dispatcher now starts in FUSE's init callback, inside the background process.
  4. Image not found after going to the background. The background process changes its folder to /, so a relative path like disk.img broke. The path is now made absolute with realpath before mounting.

The background-mount fix has a regression test in tests/system.sh: it mounts without -f, writes a file, remounts under another policy and checks the data, with timeouts so a hang fails instead of blocking.

13Limitations and future scope

Be honest here. Admitting limits clearly is a strength in a viva.

Limitations

  • No journal: a crash while mounted can leave the image inconsistent, so a clean unmount is needed.
  • Small files only: at most 1,036 blocks (about 4.05 MiB) per file, and 256 inodes per disk.
  • Fewer features than ext4: no symbolic or hard links, no chmod/chown, and rename will not replace an existing file. Opening a file checks only that it exists and is not a folder.
  • Seek is modelled: head movement is |current block − next block|. The image lives on an SSD, so we measure the scheduler's decisions, not a real disk arm.
  • Adaptive needs tuning: with the default weights it behaved almost like FCFS on the mounted workload.

Future scope

  • Add a journal and an fsck checker for crash safety.
  • Double-indirect blocks for bigger files.
  • More policies: C-SCAN, LOOK and deadline-based scheduling.
  • A block cache, and auto-tuning of α and β to the workload.
  • Log each scheduling decision for a step-by-step replay.

16Likely viva questions

Basics

What does SchedFS do?
It is a working Linux file system in user space where every block read and write waits in a queue, and a chosen disk-scheduling policy decides the order. It shows file systems, disk scheduling and synchronization working together.
What is FUSE?
Filesystem in Userspace. A small kernel module forwards each file system call on a mount point to an ordinary program, which answers it. Our program is schedfs.
Why FUSE and not a kernel module?
A FUSE file system is a normal process: it can be debugged and restarted, and a bug cannot crash the computer. The cost is extra context switches, which does not matter because we study the order of block requests, not raw speed.
Where is the disk?
It is one ordinary file, disk.img, treated as 4,096 blocks of 4 KB. Only the dispatcher thread reads or writes it, with pread and pwrite.

Flow and logic

What happens when I write to a file?
The kernel passes the call to our FUSE adapter; the file system locks the inode, finds or allocates the block, and puts a request in the queue; the dispatcher asks the scheduler for the next request, does pwrite, and wakes the caller.
How does a file find its blocks?
The inode has 12 direct pointers; after that, a single-indirect block holds 1,024 more. bmap turns "block n of this file" into a disk block number, allocating one when writing.
How is free space tracked?
With a bitmap in block 1: one bit per block. Allocation searches from a hint (the file's previous block) and wraps around once, then writes the bitmap and superblock back.
Why does the mount start the dispatcher in op_init?
FUSE calls fork() to go into the background, and only the calling thread survives a fork. Starting the dispatcher in the init callback, after the fork, keeps it alive. Before this fix the first command hung.

Scheduling

Explain FCFS, SSTF and SCAN.
FCFS serves in arrival order. SSTF serves the request nearest the head. SCAN moves in one direction serving requests on the way, then reverses, like a lift.
What is starvation and how does Adaptive prevent it?
Starvation is a request that keeps losing and waits forever, which can happen under SSTF. Adaptive subtracts a waiting-time term from the score (ageing), so an old request's score keeps improving until it is served.
What is the Adaptive formula?
score = α · distance/total blocks − β · wait/longest wait, with α = 0.7 and β = 0.3 by default. The lowest score wins. With β = 0 it is exactly SSTF.
Why did SCAN lose on the clustered trace?
The head started at 53 moving down, but every request was above it. SCAN is charged for going to block 0 before turning: 53 + 111 = 164 blocks, against 58 for FCFS. No policy wins on every workload.
How is your SCAN different from LOOK?
Our selection turns when nothing is left in the current direction, but the benchmark and unit test charge SCAN for travelling to the disk edge. That is why the textbook total is 236, not LOOK's 208.
Why are the results deterministic?
Ties are broken by arrival time and then request ID. FCFS, SSTF and SCAN give identical totals on every run; only Adaptive reads the real clock, so it can vary a little.
Is the seek distance real?
It is the textbook model, |current block − next block|. The image is on an SSD, so we measure the scheduler's choices, not physical arm movement. The benchmark adds a small delay per block moved to make differences visible.

Synchronization

Which classic problem is the queue?
The bounded-buffer (producer-consumer) problem: FUSE threads produce requests, the dispatcher consumes them, and a mutex with not_full and not_empty condition variables coordinates them.
Why is every wait inside a while loop?
A thread can wake without the condition being true (a spurious wake-up, or another thread got there first). Re-checking in a loop makes that harmless.
How do you prevent deadlock?
All threads take locks in one global order: directory, inode, inode-alloc, inode-table, bitmap, superblock, queue. A circular wait cannot form.
Why reader-writer locks on inodes?
Many threads can safely read the same file at once, but a write must be alone. A reader-writer lock allows exactly that, which is better than one mutex for reads.
What was the hardest concurrency bug?
Lost inode updates: 32 inodes share one block, so two threads could each write back their own copy and erase the other's change. An inode-table mutex fixed it, and the 4-thread test now passes every time.

Testing and process

How did you test it?
A unit test on the textbook trace, a core test with 4 threads and a remount, a real mounted test under every policy including background mode, ThreadSanitizer, and a benchmark. 25 test cases, all passing.
What happens if the computer crashes while mounted?
There is no journal, so the image could be left inconsistent; a clean unmount is required. Journaling and an fsck are future work.
What would you do with more time?
A journal, double-indirect blocks, C-SCAN and LOOK, a block cache, and auto-tuning α and β so Adaptive helps on every workload.
